# dadeumi (다듬이) — 남이 읽을 글 쓰기 흐름

사용자 외의 사람이 읽을 글은 아래 순서를 거친 뒤에 내놓는다. 순서는 바꾸지 않는다: AI 말투 제거는 문장 다듬기보다 먼저다.

```
문서 유형 정하기 → 정보 구조 만들기 → 초안 → AI 말투 제거 → 문장 다듬기 → 확인 후 게시
```

원칙의 배경은 `references/toss/00-core-principles.md`에 있다. 모든 원칙은 권장 사항이다 — 글의 목적에 맞지 않는 항목은 적용하지 않고, 적용하지 않은 이유를 한 줄로 남긴다.

## 0. 대상과 등급 판정

| 등급 | 기준 | 예 |
|---|---|---|
| 전체 흐름 | 제목·소제목이 있거나 3문단 이상인 글 | Confluence 페이지, Google Docs 문서, Jira 이슈 본문, Slack 캔버스, README·개발 문서, 블로그 글, 레포트, 민원·탄원서, 공지·장문 메일 |
| 간이 흐름 | 그보다 짧은 글 | Slack 메시지, Jira·Confluence 댓글, 카카오톡·문자, 짧은 메일 답장 |
| 스크리닝 | PR·이슈의 제목과 본문 (길이 무관) | `gh pr create`, `gh issue comment`, PR 리뷰 코멘트 |

등급은 글의 성격으로 정한다. 어떤 도구·경로로 나가는지는 등급과 무관하다.

스크리닝은 이 skill을 호출하지 않고 네 가지만 훑는다: 제목이 바뀐 내용을 구체적으로 말하는가 / 본문 첫 문단이 무엇을 왜 바꿨는지 말하는가 / 챗봇 프레임 문장·과장 관용구·장식용 이모지가 없는가(attribution 줄은 예외) / 고유명사·수치·링크가 정확한가.

대상이 아닌 것:

- 사용자가 준 원문을 그대로 올려 달라는 요청 — 손대지 않고 게시한다. 고칠 곳이 보이면 게시 전에 제안만 한다.
- 커밋 메시지, 코드 주석
- 코드·로그·명령 출력, 라벨·상태값·담당자 같은 필드 값
- 이 대화에서 사용자에게 하는 보고

메모리나 프로젝트 CLAUDE.md에 문서 형식 규칙이 있으면(예: 팀 위키의 기술문서 양식, 경영진용 요약 스타일) 2단계의 구조 판단보다 그 형식이 우선이다. 나머지 단계는 그대로 적용한다.

## 전체 흐름 (문서형)

### 1단계. 문서 유형 정하기

`references/toss/01-doc-type.md`를 읽고 그 프롬프트의 역할을 직접 수행한다. 입력 4가지(목표·독자·상황·추가 고려)는 대화 맥락에서 채운다. 맥락으로 알 수 없고 결과물을 바꾸는 항목(대개 독자)만 사용자에게 묻는다.

- 기술 문서: 학습 / 문제 해결 / 참조 / 설명 중 하나로 정하고, 그 유형의 "포함해야 할 사항"을 체크리스트로 쓴다.
- 기술 문서가 아닌 글: 같은 네 질문에 답한 뒤 장르의 통상 구조를 따른다. 제출처 양식이 있으면 양식이 우선이다.

| 장르 | 통상 구조 | 말투 |
|---|---|---|
| 블로그 | 제목 → 도입(독자가 얻을 것) → 소제목별 본문 → 마무리 | 필자의 평소 말투 |
| 레포트 | 요약 → 배경·목적 → 본론(근거) → 결론·제언 | 한다체 또는 합쇼체 |
| 민원·탄원서 | 요지(무엇을 요청하는가) → 사실관계(일시·장소·당사자) → 요청 사항 → 첨부·연락처 | 합쇼체 |
| 공지·메일 | 용건 → 필요한 맥락 → 독자가 할 일과 기한 | 조직 관행 |

산출: 유형(또는 장르)·독자·목표를 한 줄씩 정하고 사용자에게 알린다.

### 2단계. 정보 구조 만들기

`references/toss/02-structure.md`를 읽는다. 본문보다 목차를 먼저 만든다: 제목, 소제목, 각 절의 한 줄 요지. 목차에 5개 원칙(한 페이지 한 목표 / 개요 / 예측 가능한 구조 / 가치 먼저 / 효과적인 제목)의 체크리스트를 적용해 개선안 하나로 확정한 뒤 초안을 쓴다. H4 이상 깊이가 필요하면 문서를 나누는 안을 사용자에게 제안한다.

### 3단계. AI 말투 제거

`references/03-humanize.md`의 절차를 따른다. 초안 저장 → `quick-rules.md` 읽기 → 윤문 → 자체검증 6항 → 변경률 게이트(`scripts/change_rate.py`) 순이다. 변경률은 스크립트 출력값만 쓴다.

### 4단계. 문장 다듬기

`references/toss/04-sentences.md`를 읽고 윤문본의 문장마다 5개 체크리스트(필요한 정보만 / 메타 담화 최소화 / 구체적으로 / 일관되게 / 주체 분명히)를 적용한다. 3단계의 철칙은 계속 유효하다: 사실·수치·고유명사를 바꾸지 않고, 원문에 없던 상투구를 넣지 않는다. 다듬은 뒤 `quick-rules.md`의 S1 패턴이 새로 생기지 않았는지 확인한다. "독자(개발자)가 주체" 항목은 기술 문서가 아니면 "행동할 사람이 주어"로 읽는다.

### 5단계. 확인 후 게시

최종본과 함께 유형·변경률·주요 변경을 사용자에게 보여주고 게시한다. 게시는 외부에 보이는 작업이므로 사용자가 확인한 뒤에 실행한다.

## 간이 흐름 (메시지형)

1. 독자와 용건을 정한다: 누가 읽고, 읽은 뒤 무엇을 하길 바라는가. 결론이나 요청을 첫 문장에 둔다.
2. AI 말투를 걷어낸다.
   - 챗봇 프레임 문장: "물론입니다", "다음은 ~입니다", "도움이 되셨길 바랍니다"
   - 이모지·굵은 글씨·불릿 남발 (서너 줄짜리 메시지에는 불릿을 쓰지 않는다)
   - 결산·과장 관용구: "결론적으로", "이를 통해", "매우 중요합니다", "주목할 만합니다"
   - 번역투: "~에 대해", "~를 통해", "가지고 있다", "~되어진다", "~에 의해"
   - 문두 접속사("또한·따라서·즉") 반복, 중첩 완곡("~할 수 있을 것으로 보입니다")
   - 말투는 상대와의 관계에 맞는 하나(합쇼체·해요체·반말)로 유지하고, 원래보다 격식을 올리지 않는다
   - 고유명사·수치·날짜·링크는 그대로 둔다
3. 문장을 다듬는다: 한 문장에 한 생각, 메타 담화 삭제, 모호한 말 대신 구체적인 말, 용어 일관, 행동할 사람을 주어로.

두세 문단을 넘으면 `references/im-not-ai/quick-rules.md`를 읽고 전체 흐름의 3·4단계를 적용한다.

## 게시 도구가 hook에 막혔을 때

저장소의 `hooks/dadeumi-gate.js`를 hook으로 등록했다면, 글을 올리는 도구가 "dadeumi skill을 거쳐야 합니다"라는 사유로 거부될 수 있다. 이때는 Skill 도구로 `dadeumi`를 호출하고, 올리려던 글이 이 흐름을 거쳤는지 확인한 뒤(안 거쳤으면 지금 거친다) 같은 호출을 다시 시도한다. 다른 경로로 우회하지 않는다.

`gh` 명령이 스크리닝 체크리스트와 함께 거부되면 skill 호출 없이 위 "스크리닝" 네 가지만 훑고 같은 명령을 다시 실행한다.
